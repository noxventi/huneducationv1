# Technical SEO Audit — huneducation.com / tr.huneducation.com
Date: 2026-08-30
Scope: 500-page crawl of huneducation.com (`crawl.json`) plus live verification of both hosts (huneducation.com = EN, tr.huneducation.com = TR, separate WPML-linked installs). Root cause for most content-layer gaps: Yoast SEO, Yoast SEO Premium, WPML SEO and "Schema & Structured Data for WP & AMP" are installed but **inactive** (confirmed by site owner; corroborated below by zero frontend footprint from any of these plugins).

---

## Critical

### C1. Sitemap effectively empty against a ~1,050-URL site — caused by a separate broken legacy plugin, not just the inactive Yoast install
- Evidence: `robots.txt` on both hosts declares `Sitemap: https://huneducation.com/sitemap.xml` and `Sitemap: https://huneducation.com/sitemap.html`. `sitemap.xml` is a valid `sitemapindex` pointing to one child, `sitemap-misc.xml`, which contains exactly **2 `<url>` entries**: the homepage and `/sitemap.html`. `/sitemap.html` itself is not valid XML (fails as a sitemap format — confirmed via `sitemap_discovery.py`). Identical structure on tr.huneducation.com (2 URLs: TR homepage + `/sitemap.html`).
- Root cause identified: the XML is generated by **"Google Sitemap Generator" by Arne Brachhold** (`wp-content/plugins/google-sitemap-generator/sitemap.xsl`, generator version `4.1.23`), a plugin abandoned since roughly 2015/pre-WP5.5. This plugin is *active* (it is actively regenerating output with today's timestamp/Request-ID) but its post/page sitemap generation is broken or misconfigured — it emits no `sitemap-pt-*` (posts/pages/CPT) sub-files at all (`sitemap-pt-post-p1.xml`, `sitemap-pt-page-p1.xml`, `sitemap-pt-egitim-p1.xml`, `sitemap-tax-category.xml`, `sitemap-author.xml` all return 404). It also appears to intercept `/wp-sitemap.xml` (WordPress core's native sitemap URL) and returns an **empty `<urlset>`** there too — meaning WP's built-in fallback sitemap is not available either.
- Impact: ~1,050 URLs (498 EN courses, 486 TR courses, ~40 university pages, ~28 core pages) have **no sitemap discovery path**. Google/Bing must find them purely by crawling the `/courses/` pagination and internal links.
- Fix: Deactivate/delete `google-sitemap-generator` (unmaintained, conflicts with core sitemaps). Activate Yoast SEO (already installed) to generate `sitemap_index.xml` with proper post-type sub-sitemaps, or, if Yoast is not activated, simply remove the legacy plugin so WordPress core's native `/wp-sitemap.xml` takes over automatically. Resubmit the new sitemap URL in GSC/Bing Webmaster Tools for both hosts.

### C2. Zero structured data, zero hreflang, zero Open Graph tags on all 500 crawled pages (confirmed, and independently re-verified)
- Evidence: `sema` (schema types) is `[]` and `og` is `false` on all 500 rows in `crawl.json`; `hreflang` count is `0` on every row. Independently re-checked by directly fetching and grepping the homepage source on both hosts (`scratch_home.html`, `scratch_home_tr.html`): zero `application/ld+json` blocks, zero `og:`/`twitter:` meta tags, zero `hreflang=` attributes on either EN or TR homepage. `render_page.py`'s structured-data extractor independently confirms `block_count: 0` on the homepage.
- Root cause: Yoast SEO / Yoast SEO Premium (would emit JSON-LD + OG), WPML SEO (would emit `hreflang` alternates), and "Schema & Structured Data for WP & AMP" are all installed-but-inactive.
- Mitigating detail found: WPML's **language-switcher UI is functioning** — `wpml-ls-*` CSS classes and a `wpml-ls-item-tr` entry are present and wired up in the EN homepage markup, and the TR homepage links back to EN pages (e.g. `huneducation.com/about-us/`, `huneducation.com/courses/`). So cross-language *user* navigation exists; only the *SEO signal layer* (hreflang `<link>` tags, and by extension Google's language/region association) is missing. This confirms the hreflang gap is a plugin-activation gap, not a broken WPML core install.
- Impact: no rich-result eligibility (Organization/Course/Breadcrumb schema all absent), no social-share preview cards (missing og:image/og:title hurts CTR on shared links), and Google has no explicit signal associating huneducation.com/EN pages with tr.huneducation.com/TR equivalents (risk of the two hosts self-competing for shared course-topic intent).
- Fix: Activate Yoast SEO (configure Course/Organization schema for the relevant CPTs) and WPML SEO (hreflang). Once active, add reciprocal `hreflang="en"` / `hreflang="tr"` / `hreflang="x-default"` on paired course URLs — note the EN (498) and TR (486) course counts don't match 1:1, so slug-pair mapping needs to be confirmed before hreflang rollout (see "not verified" section).

### C3. No HTTP security headers at all, on either host
- Evidence: full response headers captured for both `https://huneducation.com/` and `https://tr.huneducation.com/` contain only: `Date, Server, Expires, Cache-Control, Pragma, Link, Set-Cookie, Vary, Content-Type`. Explicitly absent on both hosts (confirmed via targeted grep against the header dump): `Strict-Transport-Security` (HSTS), `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy`, `Referrer-Policy`, `Permissions-Policy`.
- Impact: no HSTS means every `http://` link or typo-navigation does one clear-text round trip before the 301 (a small SSL-stripping/MITM window); no clickjacking protection; no MIME-sniffing protection. These also directly feed Lighthouse's "Best Practices" score.
- Fix: add via `.htaccess` (Apache confirmed as the server) or a security-headers plugin:
  `Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"`
  `Header always set X-Content-Type-Options "nosniff"`
  `Header always set X-Frame-Options "SAMEORIGIN"`
  `Header always set Referrer-Policy "strict-origin-when-cross-origin"`
  `Header always set Permissions-Policy "geolocation=(), microphone=(), camera=()"`
  Roll out on huneducation.com first and confirm no third-party embed (WhatsApp widget, GTM, YouTube) breaks under a CSP before adding one; add HSTS `preload` only after confirming all subdomains (including tr.) are HTTPS-only.

## High

### H1. No caching layer — every request is `Cache-Control: no-store, no-cache, must-revalidate` and sets a fresh `PHPSESSID` cookie
- Evidence: identical header block on the homepage, the `/courses/` archive, `/courses/2/` through `/courses/25/`, individual course pages, and even 301 redirect responses: `Cache-Control: no-store, no-cache, must-revalidate` / `Pragma: no-cache` / `Set-Cookie: PHPSESSID=...; path=/`. No `CF-Cache-Status`, `X-Cache`, `Age`, or any CDN/edge-cache header on any response checked. The plugin inventory pulled from the homepage source (elementor, elementor-pro, jet-engine/elements/menu/search/tabs/tricks, google-analytics-for-wordpress/MonsterInsights, pixelyoursite, sitepress-multilingual-cms/WPML, wp-whatsapp-chat) contains **no caching plugin** (no WP Rocket/W3TC/WP Super Cache/LiteSpeed Cache) and **no image-optimization plugin**.
- Impact: every page view is a fresh, uncached PHP execution with a brand-new session; across ~1,050 live URLs this is a real TTFB/LCP risk under real traffic or crawl load, and it prevents any browser/proxy caching of HTML (repeat visits re-download the full page every time).
- Fix: install and configure a caching plugin (WP Rocket, or LiteSpeed Cache if the host runs LiteSpeed) with page caching for anonymous visitors. Separately, audit what is calling `session_start()`/setting `PHPSESSID` on every front-end request — sessions should not be created for anonymous visitors on pure content pages; gate it to only the pages that actually need session state (e.g. the contact/lead form).

### H2. Course listing pages are 650–735 KB of raw HTML each, with 36–47 separate render-blocking CSS requests and unoptimized web-font loading
- Evidence: the heaviest pages in the 500-page crawl are all `/courses/N/` pagination pages — `/courses/24/` at 735,378 bytes, `/courses/10/` at 714,402 bytes, `/courses/11/` at 710,096 bytes (site-wide average is 159,880 bytes). Direct fetch of `/courses/` and `/courses/2/` show **36 separate `<link rel="stylesheet">` requests each**, one file per Elementor widget (`widget-image.min.css`, `widget-heading.min.css`, `widget-icon-list.min.css`, `widget-social-icons.min.css`, etc.) — indicating Elementor's "Improved CSS Loading" asset combination is not enabled. On top of that, 3 full Google Fonts families are requested via the legacy blocking API with **every weight and style** (100–900, italic): `fonts.googleapis.com/css?family=Poppins:100,100italic,...,900,900italic` (same pattern for Roboto and Open Sans). Only one `preconnect` hint exists (`fonts.gstatic.com`); none to `fonts.googleapis.com` itself.
- Impact: a heavy render-blocking CSS chain plus an oversized font payload directly threatens LCP on exactly the page type (course listings) most likely to be a search entry point; the large HTML size on 25 near-identical archive pages also inflates crawl cost for no ranking benefit.
- Fix: in Elementor > Settings > Advanced, enable "Improved CSS/Asset Loading" to consolidate per-widget CSS; trim the Google Fonts request to only the weights actually used in the design (typically 2–4 per family); add `rel=preconnect` for `fonts.googleapis.com` in addition to the existing `fonts.gstatic.com` one; consider a lighter listing-card template to shrink per-page HTML weight.

### H3. 70.8% of images sitewide are missing `alt` attributes
- Evidence: aggregated across all 500 crawled pages from `crawl.json`: 2,614 `<img>` tags found in main content, 1,851 without a non-empty `alt` attribute (70.8%).
- Impact: an accessibility failure (WCAG), and a loss of image-search/alt-text ranking signal sitewide, including on all 444 crawled course detail pages.
- Fix: bulk-audit against the media library; since Elementor image widgets pull `alt` from `wp_postmeta._wp_attachment_image_alt` by default, fixing alt text at the media-library level will propagate across all usages of each image in one update.

### H4. 494/500 pages have no meta description (confirmed, independently reproduced on TR home)
- Evidence: `crawl.json` shows 494/500 EN pages with an empty `desc` field. Independently re-checked the TR homepage directly — no `<meta name="description">` present there either, confirming the gap is not EN-only.
- Impact: Google will auto-generate snippets from body copy across roughly 1,050 URLs, typically hurting CTR relative to a deliberately written description.
- Fix: activate Yoast SEO and use bulk/template variables (e.g. "%%title%% — Study %%course_name%% in Hungary | HunEducation") to backfill descriptions for the 444 EN + roughly 430 TR course pages programmatically, then hand-write descriptions for the ~28 core pages (home, about, admission, costs, contact).

### H5. Large, unbounded faceted/filtered course-search URLs are crawlable
- Evidence: the TR homepage links directly to EN filtered results such as `huneducation.com/courses/?asp_ls=&asp_active=1&p_asid=1&p_asp_data=1&aspf%5Bcourse_institute__6%5D=&termset%5Bcourse-month%5D%5B%5D=-1&...&termset%5Bcourse-category%5D%5B%5D=33&filters_initial=1&filters_changed=0&wpml_lang=en&qtranslate_lang=0&current_page_id=199` (from an Ajax-Search-Pro-style filter widget on the course archive). Confirmed by direct fetch: this URL returns `HTTP 200`, and — importantly — **self-corrects** with `<link rel="canonical" href="https://huneducation.com/courses/">` (no query string), so canonical signal consolidation is working correctly. `robots.txt` has no `Disallow` rule for query strings, so these remain freely crawlable even though not indexable.
- Impact: crawl-budget waste — every combination of course category/institute/month/year/city/level is a distinct crawlable URL returning ~650KB of HTML, even though the canonical tag protects against actual duplicate indexation.
- Fix: add a `Disallow` rule scoped to the filter parameters (e.g. patterns matching `asp_ls=`, `termset%5B`, `aspf%5B`) or configure equivalent handling in Bing Webmaster Tools' URL-parameter settings, to stop crawl-budget spend on filter permutations. Re-verify the canonical tag still resolves correctly after the robots.txt change (it should, since `Disallow` only affects crawling, not the already-indexed canonical URL).

## Medium

### M1. `/courses/` pagination set (25 pages, confirmed) has no `rel="next"/"prev"` and template-thin, near-duplicate titles
- Evidence: `/courses/`, `/courses/2/` … `/courses/25/` are 25 distinct URLs (confirmed count in `crawl.json`), each with a **correct, self-referencing canonical** — individually verified pages 1, 2, 3 and 25 each canonicalize to themselves, not to `/courses/` (no canonical-collapsing bug). However, no `rel="next"`/`rel="prev"` link tags were found on any of the checked pagination pages (direct grep against raw HTML: zero matches), and all 25 pages carry the same generic title pattern differentiated only by page number: "Courses HunEducation" / "Courses Page 2 HunEducation" / "Courses Page 3 HunEducation" / … / "Courses Page 25 HunEducation" — no unique value proposition per page, and (per H4) none of them carry a meta description.
- Impact: `rel=next/prev` is deprecated by Google (since 2019) but is still consulted by Bing; on its own this is minor, but combined with the thin/undifferentiated titling and zero meta descriptions across all 25 pages, it's a real (if secondary) weak-content signal for a 25-page URL set that has no chance of ranking for anything on its own merits.
- Fix: this is low-cost to improve — write a distinct, descriptive title/meta description template per page (if the taxonomy allows batching by featured country, degree level, or intake period, use that to differentiate). Add `rel="next"/"prev"` for Bing's benefit; optional since Google ignores it.

### M2. WordPress/plugin version disclosure via `generator` meta tags
- Evidence: the homepage `<head>` contains three separate disclosure tags: `<meta name="generator" content="WordPress 7.1" />`, `<meta name="generator" content="WPML ver:4.9.4 stt:1,53;" />`, and an Elementor generator tag disclosing `Elementor 4.1.1` plus feature flags.
- Impact: minor attack-surface fingerprinting — an attacker can target known CVEs for the exact WP/WPML/Elementor build without guessing. Not a ranking factor directly; flagged as security hygiene.
- Fix: strip the WordPress generator tag via `remove_action('wp_head','wp_generator')`, and add equivalent filters/removal for the WPML and Elementor generator tags, ideally as part of the same hardening pass as C3.

### M3. Two redirect hops for the `www` variant before reaching the canonical URL
- Evidence: `http://www.huneducation.com/` → 301 → `https://www.huneducation.com/` → 301 → `https://huneducation.com/` (2 hops, confirmed via header trace on each leg). By contrast, `http://huneducation.com/` → 301 → `https://huneducation.com/` is a clean single hop.
- Impact: minor extra latency/crawl-budget hop for any inbound link built with a `www.` prefix; low volume concern but easy to eliminate.
- Fix: add a single rewrite rule sending both `http://www` and `https://www` directly to `https://huneducation.com` in one hop, instead of protocol-upgrading the `www` host first and only then stripping `www`.

### M4. Duplicate `<title>` tags across distinct URLs
- Evidence: 17 duplicate-title groups spanning 34 pages in the 500-page crawl, including exact duplicate pairs such as "Electrical Engineering BME HunEducation", "Chemical Engineering BME HunEducation", "Computer Science Engineering BME HunEducation", "MA Sociology HunEducation" — same title text, different URLs.
- Impact: title-tag collisions between distinct course entries either indicate genuinely duplicate/near-duplicate course listings (worth a content audit) or a title template that fails to disambiguate variants (e.g. the same course offered at two intake dates or degree levels).
- Fix: confirm with the content team whether each of the 17 pairs is a true duplicate (merge + 301 if so) or a legitimate variant (extend the title template with a differentiator such as intake term, degree level, or campus).

## Low

### L1. Case-insensitive URLs resolve without a normalizing redirect
- Evidence: `https://huneducation.com/COURSES/` returns `HTTP 200` directly (no redirect to the lowercase `/courses/`), serving equivalent content.
- Impact: a theoretical duplicate-path exposure if any external link ever uses mixed case. Real-world risk is low since all internal links are consistently lowercase; canonical tags are template-generated from the resolved permalink rather than the raw request path, so they likely still self-correct to the lowercase canonical — but I did not fetch-and-confirm the canonical tag value from the uppercase request itself (see "not verified" below).
- Fix: add a case-normalizing redirect at the webserver level if straightforward in the current Apache config; low priority otherwise.

### L2. Crawlability is otherwise clean (pass, listed for completeness)
- Evidence: 0/500 crawled pages carry a `noindex` robots meta tag; 0/500 were blocked by `robots.txt` (the crawler's own blocked-URL list is empty); `robots.txt` on both hosts only disallows `/wp-admin/` (with `admin-ajax.php` correctly carved out as `Allow`) — a minimal, correct configuration with no over-blocking.

### L3. No JS-rendering dependency (pass, listed for completeness)
- Evidence: `render_page.py --mode auto` against the homepage reports `is_spa: False`, and the automatic SPA-shell detector did not even trigger a Playwright render — meaning full content, titles, and links are present in the raw server response. The site is Elementor-generated static HTML, not client-side rendered.
- Google/Bing do not need to execute JavaScript to see course content, titles, or internal links.

### L4. Mobile viewport correctly configured (pass, listed for completeness)
- Evidence: `<meta name="viewport" content="width=device-width, initial-scale=1">` is present and correctly configured on both the EN and TR homepages (independently confirmed on both hosts).

### L5. Canonical tag implementation is technically correct across the crawled set (pass, worth stating explicitly)
- Evidence: across all 500 crawled EN pages, 0 have a canonical pointing to a different URL than themselves (aside from the expected `/courses/N/` self-referencing pagination canonicals, individually verified), 0 canonicalize cross-domain to tr.huneducation.com, and only 1 page (the single 404) has an empty canonical field.
- This directly answers the audit brief's "canonical correctness (incl. cross-language)" ask: no cross-language canonical leakage was found in the crawled set.

## What I could NOT verify (flagging so the report does not overclaim)

- **IndexNow / "Instant Indexing" plugin behavior**: no supporting evidence found — no IndexNow key file at the domain root, no "indexnow"/"rankmath"/"instant indexing" string anywhere in the homepage source, and best-effort probes against a few known plugin-slug `readme.txt` paths (`wp-indexnow`, `index-now`, `rank-math-pro`) all returned 404. This suggests no active IndexNow integration, but I was not able to browse the actual wp-admin plugin list or a full plugin-directory listing, so absence of frontend evidence is not fully conclusive (some IndexNow implementations submit purely server-side/via cron with no frontend footprint). **Recommend confirming directly in wp-admin > Plugins.**
- **Canonical tag value specifically on the uppercase `/COURSES/` request** (L1) — confirmed the page returns 200 with content, but did not re-fetch that exact response and inspect its canonical tag value.
- **Course catalog EN↔TR slug-pair mapping** (referenced under C2) — I did not build a full 498×486 URL-pair comparison; the roughly 12-course gap between the EN and TR catalogs is inferred from counts already supplied, not independently reconciled URL-by-URL. This should be done before rolling out hreflang pairs.
- **Course-page average word count**: measured directly from `crawl.json`'s word-count field for all 444 crawled `/course/{slug}/` singular pages: average 445.1 words, minimum 318, maximum 1,482 — zero pages under 150 words. This is higher than an earlier ~330-word estimate raised during this audit; flagging the discrepancy rather than silently adopting either figure. Either way, the conclusion holds: thin content is not a real issue on course detail pages.
- **Full Core Web Vitals field/lab data** (actual LCP/INP/CLS measurements in milliseconds): this audit is source-and-header inspection only — no CrUX/PageSpeed Insights API call and no Lighthouse run were performed. Findings above (H2 in particular: unoptimized fonts, missing image dimensions, no caching layer) are risk indicators derived from HTML/header inspection, not measured metric values, and should be confirmed with a real PSI/CrUX pull before prioritizing engineering time.
- **Working-folder artifacts** (`screenshots/`, `render-home.json`, `render-home.err`, `t.html`) present in the audit directory were not incorporated into this analysis — treated as prior working files and not re-verified against the findings above.

## Score: 32/100

Rationale: the site is technically reachable, crawlable, and correctly canonicalized — clean redirect behavior, no noindex/robots blocking, no JS-rendering dependency, correct mobile viewport, and zero canonical mismatches across all 500 crawled pages. But it is failing on almost every layer that actually drives visibility and click-through at scale: no working discovery path for roughly 1,050 URLs (a broken legacy sitemap plugin), zero structured data/hreflang/Open Graph sitewide, zero HTTP security headers, no caching layer on a template-heavy Elementor+Jet stack, and 70.8% of images missing alt text. Nearly all of this traces back to a small, fixable set of causes — reactivate three or four already-installed plugins, remove one abandoned plugin, add a caching layer, and add one security-headers rule — which is why the score is low while the fix effort is disproportionately small relative to the impact.
