# Sitemap & Indexation Audit — huneducation.com / tr.huneducation.com

Audit date: 2026-08-30
Scope: XML sitemap architecture, indexation exposure, WPML domain-per-language sitemap design, course-page index-bloat decision.

---

## 1. Executive Summary

Both hosts run the same broken sitemap configuration. The declared, functioning sitemap chain
on each domain exposes **2 URLs** (the homepage and a navigational `/sitemap.html` utility page)
against a true site inventory of **~1,052 URLs** (14 EN + 14 TR core pages, 498 EN + 486 TR
`/course/` pages, 20 + 20 `/university/` pages). That is **~0.2% sitemap coverage of real content**.

A second, fully-populated sitemap system exists on the server (WordPress core's native
`wp-sitemap.xml` provider, confirmed by its distinct `wp-sitemap.xsl` stylesheet) and contains
**every** course/university/page URL with correct per-URL `lastmod` values — but its master index
has been overwritten/emptied by the active "XML Sitemap Generator for Google" plugin, and its
individual child files respond with **HTTP 404** despite serving valid-looking XML bodies. This
system is orphaned and not usable by search engines as-is.

Compounding this, **zero hreflang signals exist anywhere** — not in `<head>` on any of 500 crawled
pages, and not in any sitemap (`xhtml:link` is absent because the active sitemap generator plugin
predates/ignores WPML). On a WPML domain-per-language deployment (EN on huneducation.com, TR on
tr.huneducation.com) this means Google has **no machine-readable relationship between the two
language versions of the site at all** — sitemap or on-page.

The underlying pages themselves are largely healthy from a crawlability standpoint (499/500
crawled URLs = 200, 0 noindex, 0 canonical mismatches), so this is a **discovery/architecture
failure layered on top of indexable content**, not a fundamental content-blocking problem — which
makes it a high-value, low-risk fix.

**Score: 14/100**

## 2. Current State — Host by Host

### 2.1 huneducation.com (EN)

```
robots.txt:
  Sitemap: https://huneducation.com/sitemap.xml
  Sitemap: https://huneducation.com/sitemap.html      <- INVALID: not a machine-readable sitemap format
```

- `sitemap.xml` → `<sitemapindex>` generated by **XML Sitemap Generator for Google v4.1.23**
  (Auctollo `google-sitemap-generator` plugin). Contains exactly **1 child**: `sitemap-misc.xml`.
- `sitemap-misc.xml` → `<urlset>` with exactly **2 `<url>` entries**: the homepage
  (`lastmod=2024-05-20T21:03:21+00:00`) and `/sitemap.html` (`lastmod=2026-07-08T12:12:13+00:00`).
  Both carry deprecated `<priority>`/`<changefreq>` tags.
- `sitemap.html` (declared in robots.txt as a "Sitemap:") is an HTML page, not valid sitemap XML —
  confirmed invalid by the discovery tool (`"kind": null, "valid": false, "error": "invalid XML"`).
  It links to exactly 1 sub-page, `sitemap-misc.html`.
- `wp-sitemap.xml` (WordPress core's native path) is **also intercepted by the same plugin** and
  returns `200 OK` with an **empty** `<urlset>` (should be a `<sitemapindex>` per WP core spec if
  functioning — it is neither functioning nor absent, it's a dead stub).
- **Orphaned native sitemap files exist and are fully populated**, confirmed by fetching guessed
  paths directly:

  | File | Status | `<loc>` count | Content |
  |---|---|---|---|
  | `wp-sitemap-posts-course-1.xml` | **404** | 498 | Real course URLs, real per-URL `lastmod` |
  | `wp-sitemap-posts-university-1.xml` | **404** | 20 | Real university URLs |
  | `wp-sitemap-posts-page-1.xml` | **404** | 14 | Real core pages (home, why-hungary, courses, about-us, admission, costs, etc.) |
  | `wp-sitemap.xsl` | 200 | n/a | Native WP stylesheet (confirms this is WP core, not the plugin) |

  Every one of these returns HTTP **404 Not Found** in the header while streaming a fully-formed,
  correct `application/xml` body with real content — verified reproducibly across 3 repeat
  requests each. A sitemap file served with a non-200 status is **rejected by Search Console and
  Googlebot regardless of body content**, so even if these URLs are guessed/discovered, they will
  not be trusted or processed.

## 3. Root Cause

The active **"XML Sitemap Generator for Google" v4.1.23** (Auctollo, last meaningfully updated
years ago) is:

1. Generating a `sitemap-misc.xml` that only ever included the "misc pages" bucket (home +
   itself) — it was never configured (or was configured before the `course`/`university` custom
   post types existed) to include those post types as sitemap sources.
2. Simultaneously claiming the `/wp-sitemap.xml` route that WordPress core (5.5+) uses for its
   built-in sitemap, overwriting it with an empty stub. This breaks the native WP sitemap index
   without actually replacing its functionality, and leaves the native per-post-type child
   endpoints (`wp-sitemap-posts-course-1.xml`, etc.) responding 404 despite still rendering their
   provider output — a rewrite-rule/routing conflict between the two systems.
3. Yoast SEO, which ships a modern, post-type-aware, W3C-valid sitemap module (and would resolve
   both defects above out of the box), **is installed on this site but inactive**.

This is a plugin-conflict problem with a known-good, already-installed fix sitting unused, not a
fundamental platform limitation.

---

## 4. Exact Fix

1. **Deactivate** "XML Sitemap Generator for Google" (Auctollo) on **both** WordPress
   environments (EN and TR — confirmed active on both via identical version fingerprint).
2. **Activate Yoast SEO** on both. Confirm its XML Sitemaps module is enabled (default on).
   Flush permalinks (Settings → Permalinks → Save) on both after deactivation so WP's rewrite
   rules regenerate cleanly and no route conflict persists.
3. In Yoast, verify the `course` and `university` custom post types are **not** excluded from the
   sitemap (Yoast → Settings → Content Types), so they get their own child sitemap automatically.
4. Update both `robots.txt` files:
   - Remove `Sitemap: https://<host>/sitemap.html` (invalid entry, not machine-readable XML/TXT).
   - Replace `Sitemap: https://<host>/sitemap.xml` with the new Yoast index,
     `https://<host>/sitemap_index.xml`.
5. Re-submit `https://huneducation.com/sitemap_index.xml` and
   `https://tr.huneducation.com/sitemap_index.xml` in their respective Search Console properties
   (verify a TR-specific GSC property exists — flag as an open action item if not).
6. Do not leave the legacy plugin's sitemap files live post-cutover; once Yoast is confirmed
   healthy, let the old `sitemap.xml`/`sitemap-misc.xml`/`sitemap.html` routes 404 naturally
   (do not need special redirects — they were never meaningfully indexed given the coverage gap
   above).

## 5. Target Sitemap Architecture for This WPML Domain-Per-Language Setup

**Per-host index (keep the current split — it is correct):**
- `https://huneducation.com/sitemap_index.xml` — declared only in `huneducation.com/robots.txt`
- `https://tr.huneducation.com/sitemap_index.xml` — declared only in `tr.huneducation.com/robots.txt`

Do **not** try to unify EN and TR into a single cross-domain sitemap file — with domain-per-language
WPML, each domain is its own crawlable root/GSC property and must self-declare its own index.

**Per-post-type children, one file per type per host** (all well under the 50k URL / 50MB cap, no
pagination needed at current volumes):
- `sitemap-pages.xml` — 14 core pages
- `sitemap-course.xml` — 498 (EN) / 486 (TR) course CPT entries
- `sitemap-university.xml` — 20 / 20 university CPT entries
- Omit a taxonomy/category sitemap unless those archive pages are canonical, indexable, and
  actually intended as landing pages — don't add index bloat for non-canonical archives.

**`lastmod` policy:** use the post's true `post_modified_gmt` (already correct and varied in the
orphaned native provider — e.g., real per-course timestamps like `2025-02-22T20:33:26+00:00`),
not a blanket "generated-on" plugin timestamp. Two problems to fix during migration:
- The current live homepage `lastmod` (2024-05-20) is stale relative to a site that is clearly
  still being edited (TR home shows 2026-05-18, other TR utility pages 2026-07-08) — inconsistent
  freshness across the (broken) sitemap is itself a Low-severity flag once the set is real again.
- `lastmod` should reflect **significant content edits** (price, curriculum, dates, copy), not
  every trivial re-save (widget/plugin metadata touches). WordPress bumps `post_modified` on
  nearly any save; if Yoast's dates look artificially "always today" after cutover, that's a sign
  a caching/optimization plugin or scheduled resave job is touching post rows without real edits.
- Drop `priority`/`changefreq` entirely (Yoast does not emit them by default — correct; Google
  has ignored both since ~2012).

**`xhtml:link` alternates — use them, but as a secondary signal, not the primary fix:**
- The absence of hreflang here is total: no on-page `<link rel="alternate" hreflang>` tags on any
  of 500 crawled pages, and no `xhtml:link` in any sitemap. On a WPML domain-per-language site
  this is the single highest-leverage indexation fix available, because Google currently has
  **no signal at all** connecting `huneducation.com/course/medicine-bsc/` to its TR equivalent —
  risk of wrong-language SERP serving and no consolidated language/region equity.
- **Priority 1: enable WPML's native hreflang output** (WPML → Languages → Search Engine
  Optimization → "Add hreflang language and region meta tags"). This is a built-in toggle already
  paid for and is the standard, most reliable mechanism (on-page, present on every request,
  independent of sitemap freshness).
- **Priority 2, additive: mirror the same relationships as `xhtml:link` in each sitemap** once a
  WPML↔Yoast integration is active, using WPML's translation-relationship API — not a naive
  "swap the domain" mapping. This matters because EN and TR catalogs are **not 1:1** (498 EN vs
  486 TR courses — a 12-course gap). Only emit `xhtml:link` alternates for URLs with a genuine
  WPML-linked translation; use `x-default` pointing at the source-language version for
  untranslated items. Do not fabricate alternates for the 12 mismatched courses.
- Sitemap-level hreflang is explicitly supported by Google as an alternative/supplement to
  on-page tags, but it only helps if it's reciprocal and accurate — do not ship it before the
  on-page fix, and do not ship it as a substitute for the on-page fix.

## 6. Should All ~984 Course Pages Be in the Sitemap? (Bloat vs. Discovery)

**Position: include them, but gate inclusion on a content-remediation pass — do not ship them
into the new sitemap unmodified, and do not exclude them indefinitely either.**

Evidence gathered (crawl.json, n=500 crawled URLs, 444 of them `/course/`):

| Signal | Finding |
|---|---|
| Word count | Healthy by raw length: min 318, median 419, max 1,482 words — **not** classically thin (<300w) |
| Meta descriptions | **443/444 (99.8%) empty** — no per-page differentiation in SERP snippets |
| Structured data | **0/444** have any schema.org markup (no `Course`/`EducationalOccupationalProgram`) |
| Duplicate title/H1 | **15 groups, 30 pages** with identical `<title>` and `<h1>` — true duplicates, independent of the general template question |
| Canonical | 0 mismatches — self-referential, technically clean |
| Content overlap (sampled) | Two course pages (`medicine-pecs-university` vs `medicine-bsc`) share **~48% of 6-word sequences** — i.e. roughly **52% unique content**, below the 60% quality-gate bar. **Sample size n=2 — directional, not exhaustive; recommend a full-corpus similarity pass before final go/no-go.** |
| Scale | 984 course+university pages is **~20x over** the 50-page HARD STOP threshold in this audit's quality gates |

By page count alone, this trips the **HARD STOP** gate and requires explicit user sign-off before
mass-submission. By content character, these pages are closer to a legitimate **product catalog**
(differentiated by subject, degree level, and university — a real multi-variable entity) than to
a classic doorway pattern (single variable like city name swapped over identical boilerplate).
That distinction is what keeps this in "include with remediation" territory rather than "exclude."

Recommended sequence:
1. **Do not block sitemap inclusion outright.** These are live, 200-status, non-noindexed,
   canonically-clean pages already being crawled organically (444 of the top 500 crawled URLs are
   course pages) — removing them from the sitemap doesn't stop indexing, it only slows discovery
   and recrawl prioritization for a deep, currently low-authority section. At ~984 URLs the
   sitemap is nowhere near the 50k/50MB technical ceiling, so there is no *hard* technical
   argument for exclusion.
2. **Fix the 15 duplicate title/H1 groups first** — these are unambiguous duplicate-content
   violations regardless of the broader thin-content debate; highest ROI, smallest effort.
3. **Populate unique meta descriptions programmatically** from existing structured fields
   (university name, degree type, duration, language of instruction) — closes the 99.8% gap
   cheaply and directly improves per-page differentiation.
4. **Add `Course`/`EducationalOccupationalProgram` schema** — free differentiation signal for
   both Google and the doorway-page heuristic, and enables rich results.
5. **Re-run a full-corpus (not n=2) near-duplicate content check** after steps 2–4. If measured
   unique-content ratio clears 60%+ site-wide, proceed with full inclusion. If a subset remains
   below the bar, prioritize consolidating or noindexing those specific low-differentiation pages
   rather than the whole catalog.
6. Ship `sitemap-university.xml` (40 URLs total) and `sitemap-pages.xml` (28 URLs total)
   **immediately** — well under the 30-page warning threshold, healthier word counts (405–1,341),
   no scale-driven risk.
7. Per this audit's HARD STOP protocol: since course+university pages exceed 50 pages, **explicit
   user justification is required before mass sitemap submission** — this report surfaces that
   requirement; sign-off should be obtained by the site owner/stakeholder before step 5's rollout,
   informed by the remediation status.
